# brs-to-spec vs BMAD-style Methods

This page explains how brs-to-spec differs from BMAD-style agentic delivery methods, and where the two approaches are complementary.

---

## Core identity

**brs-to-spec** is an artifact-first, delivery-readiness framework. It turns enterprise BRS and architecture input into governed, story-scoped, AI-safe engineering handoff packages using persona-routed skills.

**Personas do not own the process. Artifacts own the process. Personas execute registered skills against artifacts.**

---

## Comparison

| Question | BMAD-style methods | brs-to-spec |
|---|---|---|
| What drives the process? | Agents/personas | Artifacts, gates, and workflow state |
| Typical starting point | Product idea, PRD, feature concept | Enterprise BRS and architecture input |
| Governance model | Depends on method setup | Built into artifacts, readiness gates, and decision records |
| Persona role | Central process actors | Controlled skills selected by workflow need |
| Output focus | Agile/product/development artifacts | Story-scoped AI-safe handoff packages |
| Best fit | AI-native product delivery | Enterprise requirements readiness |

---

## Why the distinction matters in enterprise contexts

BMAD-style methods are agent-first. Personas drive the conversation, and the output depends on how well those personas are configured and how faithfully they are followed.

brs-to-spec is artifact-first. The workflow state file tracks which artifacts exist, which are stale, which quality gates were triggered, and what the next stage is. Personas only enter the picture when a specific skill is needed — and each skill produces a defined artifact against defined done criteria.

In enterprise delivery, governance is not optional. Requirements traceability, quality gate decisions, architecture sign-off, readiness records, and handoff accountability all need to be captured in durable, reviewable artifacts. The framework's artifact ownership model makes this possible without adding bureaucratic overhead.

---

## Where they are complementary

brs-to-spec can prepare the governed, traceable input that BMAD-style delivery or other coding-agent workflows can consume.

The handoff packages produced by brs-to-spec — story folders with proposal, design, tasks, and accepted quality gate artifacts — are exactly the kind of scoped, well-defined input that a coding agent or BMAD-style workflow needs to implement safely.

Use brs-to-spec to move from enterprise BRS to a governed, story-ready delivery package. Then use BMAD-style methods, Copilot, Codex, or Cursor to implement story by story.

---

## What brs-to-spec does not do

It does not:
- Replace agentic coding workflows
- Manage a product backlog or sprint board autonomously
- Build the software itself

It creates the upstream foundation that makes those downstream tools safe to use.
