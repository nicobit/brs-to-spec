# Context Drift Detection And Freshness Rules Spec

This document defines a first draft of the framework's context drift detection and freshness model.

Its purpose is to make the framework explicitly aware of when downstream AI-consumed context may no longer reflect the latest approved upstream reality.

## Objective

Define how the framework should recognize, classify, and respond to stale or potentially stale task context so that:

- downstream AI agents do not silently act on outdated assumptions
- handoff artifacts remain trustworthy
- users know when regeneration, re-review, or re-approval may be required

This spec complements the per-task context packaging model and the artifact precedence model by adding time and change sensitivity to context authority.

## Problem statement

The framework is strong at creating structured artifacts and sequencing them through stages. However, once downstream handoff artifacts or implementation tasks exist, the framework does not yet appear to make freshness an explicit operational concern.

This creates risk because a downstream artifact may remain structurally complete while no longer being materially valid.

Common examples:

- business requirements are updated after readiness
- architecture rules change after handoff generation
- a required quality gate is revised after a task package is already in use
- brownfield impact understanding improves after implementation planning

Without drift detection, the framework risks false confidence in downstream execution readiness.

## Scope

This spec applies to:

- handoff artifacts
- implementation task packages
- review task packages
- design or delivery-spec context bundles
- readiness-sensitive downstream work

This spec does not yet define:

- automation or tooling implementation
- file metadata format
- state-storage design
- notification mechanics

It defines the framework behavior and rules only.

## Core principle

Context is not only correct or incorrect. It is also current or stale.

A context package should be considered valid only if:

- its governing sources are still current enough
- no material upstream change has invalidated its assumptions
- any detected freshness risk is visible to the user or AI consumer

## Definitions

### Fresh context

Context whose governing upstream sources have not materially changed since the package or downstream artifact was created or last validated.

### Potentially stale context

Context where an upstream change occurred that may affect the downstream package, but the impact has not yet been assessed.

### Stale context

Context where a material upstream change is known to affect the downstream package and the package has not yet been refreshed or revalidated.

### Drift event

A change in an upstream artifact or decision that may affect the validity of downstream context.

### Material change

A change that can alter:

- scope
- constraints
- acceptance expectations
- architecture boundaries
- implementation assumptions
- quality or release conditions

Editorial or cosmetic changes should not be treated as material by default.

## Freshness states

The framework should conceptually support at least these states for downstream context packages and handoff artifacts:

- fresh
- review-needed
- stale

### Fresh

No known material upstream drift affects the context.

### Review-needed

An upstream change occurred that may affect the context, but impact has not yet been classified.

### Stale

An upstream change materially affects the context, so the package should not be treated as execution-safe until refreshed or revalidated.

## Drift sources

The framework should treat the following as primary drift sources.

### 1. Requirement drift

Examples:

- BRS or business-intake scope changes
- acceptance intent changes
- business constraints or exclusions change

Possible downstream impact:

- task scope invalidation
- traceability mismatch
- readiness invalidation

### 2. Architecture drift

Examples:

- architecture rules change
- architecture review introduces new constraints
- interface or integration implications change

Possible downstream impact:

- invalid implementation approach
- outdated design assumptions
- missing validation requirements

### 3. Planning drift

Examples:

- delivery structure changes active slice boundaries
- story decomposition changes
- active deliverable selection changes

Possible downstream impact:

- wrong task granularity
- incorrect task ordering
- stale handoff package scope

### 4. Readiness or gate drift

Examples:

- readiness decision changes
- a previously optional gate becomes required
- a required gate adds new constraints

Possible downstream impact:

- downstream work should pause
- implementation constraints change
- release assumptions become invalid

### 5. Brownfield-impact drift

Examples:

- existing-system-impact analysis reveals new compatibility risk
- operational dependency or rollback sensitivity is discovered later

Possible downstream impact:

- heightened regression risk
- missing safeguards in implementation tasks

## Drift impact classes

Not every drift event should have the same consequence.

The framework should distinguish at least these impact classes:

### Low impact

The change is visible but unlikely to affect execution materially.

Suggested response:

- keep context usable
- optionally mark for awareness

### Medium impact

The change may affect execution or review, but the effect is not yet confirmed.

Suggested response:

- mark as review-needed
- reassess package before execution continues

### High impact

The change materially affects governed constraints, task scope, or acceptance expectations.

Suggested response:

- mark as stale
- require refresh, regeneration, or revalidation before use

## Drift rules by artifact family

### Business and requirements artifacts

Material requirement changes should trigger review of:

- delivery structure
- traceability
- readiness context
- active handoff artifacts

If the change alters active deliverable scope or acceptance expectations, downstream task context should be treated as stale.

### Architecture artifacts

Changes to `architecture-rules.md` should be treated as high-sensitivity drift because these are governing constraints.

Changes to `architecture-review.md` may be medium or high impact depending on whether they revise active implementation implications.

### Planning artifacts

Changes to `delivery-structure.md` should be evaluated for whether they alter:

- the active slice
- story boundaries
- dependency assumptions

If yes, downstream task packaging may require refresh.

### Readiness and quality-gate artifacts

Any change that affects permission to proceed or adds mandatory constraints should be treated as at least medium impact and often high impact.

### Handoff artifacts

Handoff artifacts are drift receivers, not primary drift sources in this model.

They should inherit freshness state based on their upstream dependencies.

## Dependency concept

Each downstream package or handoff artifact should be understood as depending on a finite set of upstream artifacts.

Freshness should be evaluated against those dependencies, not against all initiative artifacts indiscriminately.

This means drift detection should later be dependency-aware rather than globally noisy.

## Minimum dependency categories

For an implementation task, likely dependency categories include:

- task contract
- design or delivery-spec context
- architecture constraints
- readiness constraints
- relevant quality-gate outputs
- relevant acceptance intent

For a handoff-generation task, likely dependency categories include:

- delivery structure
- architecture review
- architecture rules
- readiness decision
- required gates
- traceability inputs where applicable

## Response model

When drift is identified, the framework should conceptually respond in one of these ways:

### 1. Awareness only

Used when the change is visible but not likely to affect the current downstream task materially.

### 2. Review-needed

Used when the impact is uncertain and a human or framework check should determine whether refresh is required.

### 3. Refresh-required

Used when the downstream artifact or task package should not continue to be treated as current until updated or revalidated.

## Freshness decision flow

When an upstream change occurs, the framework should conceptually assess freshness in this order:

1. Identify which downstream artifacts or packages depend on the changed source.
2. Determine whether the change is material.
3. Determine likely impact level.
4. Mark downstream context as fresh, review-needed, or stale.
5. Indicate whether refresh, regeneration, or re-approval is required.

## Packaging implications

The packaging model should surface freshness information explicitly.

At minimum:

- the package should identify its governing upstream dependencies
- the package should identify whether freshness is confirmed, uncertain, or invalidated
- stale authoritative context should never be silently bundled as if current

## Precedence implications

Freshness does not replace authority.

Instead:

- precedence decides which source wins
- freshness decides whether the winning source is still safe to rely on

An authoritative artifact that is stale should trigger refresh or review, not blind obedience.

## Brownfield implications

Brownfield work should be treated as especially drift-sensitive because new implementation reality often emerges after initial planning.

Examples:

- actual repo conventions differ from assumed architecture narrative
- hidden integration dependencies are discovered late
- rollback constraints become clearer after delivery planning

Brownfield drift should therefore be assessed not only from formal document updates, but also from newly discovered implementation constraints when those become governed decisions.

## Non-goals

This model is not intended to:

- treat every upstream edit as a blocking event
- replace readiness or approval workflows
- require immediate regeneration for cosmetic changes
- make freshness judgment fully automatic at the conceptual stage

## Success criteria

The drift and freshness model will be useful when:

- the framework can distinguish fresh, review-needed, and stale downstream context
- users can see when handoff artifacts are no longer trustworthy
- material upstream changes trigger appropriate downstream review or refresh
- AI consumers are less likely to act on outdated context silently

## Example drift summary

In simplified form, the framework should behave like this:

- if upstream change is non-material, keep context fresh or awareness-only
- if upstream change may affect the task, mark review-needed
- if upstream change changes constraints, scope, or acceptance materially, mark stale and require refresh

## Open questions for next iteration

These questions should be refined in later design work:

- what exact changes count as material per artifact family?
- how should freshness be represented in workflow-state or artifact metadata?
- should some drift types block implementation automatically?
- what is the minimal useful refresh process for stale task packages?
- how should multi-repository handoff freshness be tracked when only one repo slice is impacted?

## Recommended next step

The next design step after this spec should be to define retrieval guidance by task type, role, and delivery mode so that context selection can use packaging, precedence, and freshness together.
