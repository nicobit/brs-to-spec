# Artifact Precedence And Conflict-Resolution Spec

This document defines a first draft of the framework's artifact precedence and conflict-resolution model.

Its purpose is to ensure that when multiple artifacts provide overlapping, inconsistent, or differently scoped guidance, the framework can determine which source has authority for downstream AI-assisted work.

## Objective

Define a deterministic authority model for framework artifacts so that:

- AI consumers receive context with clear source priority
- conflicting instructions are resolved consistently
- implementation and review work do not depend on implicit interpretation of artifact importance

This spec is intended to complement the per-task context packaging model by defining how authority is handled inside a packaged context bundle.

## Problem statement

The framework already separates artifacts by purpose and stage, but precedence is still mostly implicit.

That works reasonably well for human readers, but AI-assisted workflows need stronger determinism. When two artifacts differ in detail, timing, or intent, the framework should not rely on the user or agent to infer which one should win.

Without a clear precedence model, the framework risks:

- contradictory implementation guidance
- inconsistent task generation
- weak handling of stale summaries versus current constraints
- reduced trust in downstream prompts and handoff artifacts

## Scope

This spec applies to framework artifact authority during:

- task packaging
- handoff generation
- AI implementation
- implementation review
- readiness and gate interpretation

This spec does not yet define:

- automated conflict detection
- tooling behavior
- version-comparison logic
- document formatting changes

It defines the authority model and resolution rules only.

## Core principle

Not all artifacts are equal in authority.

Artifact authority should be determined by:

- decision proximity: how directly the artifact governs the active task
- governance strength: whether the artifact records an approved constraint or merely provides context
- specificity: whether the artifact is initiative-specific, deliverable-specific, or generic
- recency and freshness: whether the artifact reflects the latest approved state

## Precedence model

The framework should use four authority tiers.

### Tier 1: Governing constraints

These artifacts define mandatory boundaries and rules that downstream work must obey.

Examples:

- `architecture/architecture-rules.md`
- required quality-gate outputs
- approved contract definitions
- readiness constraints that explicitly limit implementation or release behavior

Authority rule:

- Tier 1 artifacts override all lower-tier artifacts when they conflict on a governed matter

### Tier 2: Approved task and deliverable contracts

These artifacts define what the active deliverable or task is expected to do.

Examples:

- `openspec/changes/.../tasks.md`
- `openspec/changes/.../design.md`
- `standalone-delivery/.../delivery-spec.md`
- approved validation expectations tied to the active task

Authority rule:

- Tier 2 artifacts govern the active unit of implementation or review
- they are subordinate to Tier 1 constraints
- they override broader narrative or planning summaries when those are less specific

### Tier 3: Initiative-specific planning and interpretation artifacts

These artifacts provide the initiative-specific context that shapes delivery but does not usually override direct implementation contracts or formal constraints.

Examples:

- `planning/delivery-structure.md`
- `planning/traceability-matrix.md`
- `architecture/architecture-review.md`
- `business-intake/business-intake-summary.md`
- `architecture/existing-system-impact.md`

Authority rule:

- Tier 3 artifacts provide shaping and interpretation context
- they should influence task generation and review reasoning
- they should not override Tier 1 or Tier 2 decisions when a direct conflict exists

### Tier 4: Generic guidance and reference material

These artifacts help structure work but are not authoritative for initiative-specific execution.

Examples:

- generic templates
- framework guidance documents
- example artifacts
- optional planning projections such as `gitlab-planning-view.md`

Authority rule:

- Tier 4 artifacts should never override initiative-specific approved artifacts
- they are reference aids only unless explicitly adopted into higher-tier initiative artifacts

## General precedence rules

### Rule 1: Higher authority tier wins

If two artifacts conflict on the same question, the higher authority tier prevails.

### Rule 2: More specific artifact wins within the same tier

If two artifacts are in the same tier, the more specific one should prevail.

Examples:

- active-deliverable design guidance should outrank broad initiative planning within the same authority class
- story-specific contract detail should outrank feature-level summary guidance

### Rule 3: Fresher approved artifact wins within the same tier and scope

If two artifacts have the same authority tier and similar scope, the newer approved artifact should prevail, provided it is valid and not stale itself.

### Rule 4: Governed constraint beats convenience

If a planning or implementation convenience conflicts with a governed rule, the governed rule prevails even if the lower-tier artifact is more detailed.

### Rule 5: Initiative-specific artifact beats generic framework guidance

A generic template or guideline may inform structure, but it should not override an approved initiative-specific decision.

### Rule 6: Human approval status matters

An approved artifact should outrank an unapproved draft of otherwise similar scope unless the approved artifact is known to be stale and superseded through explicit governance.

## Conflict categories

The framework should recognize at least these conflict types.

### 1. Constraint conflict

Example:

- a task suggests an implementation approach that violates architecture rules

Resolution:

- architecture rules prevail

### 2. Scope conflict

Example:

- planning summary says one thing, but the approved task narrows or changes the active implementation unit

Resolution:

- approved task artifact prevails for execution scope

### 3. Freshness conflict

Example:

- handoff artifact reflects an older readiness or architecture state

Resolution:

- the fresher authoritative source prevails and the handoff should be treated as stale or review-required

### 4. Specificity conflict

Example:

- broad initiative architecture review suggests one pattern, but the active story design defines a narrower approved approach consistent with higher-level rules

Resolution:

- the more specific approved artifact prevails if it does not violate higher-tier constraints

### 5. Narrative-versus-contract conflict

Example:

- business-intake narrative implies behavior that the approved task contract does not include

Resolution:

- the implementation task should follow the approved task contract
- the narrative mismatch should be surfaced as a planning or traceability issue, not silently implemented

## Resolution workflow

When a conflict is identified, the framework should conceptually resolve it in this order:

1. Determine whether the conflict concerns a governed constraint, scope definition, interpretation detail, or narrative context.
2. Compare the authority tier of the relevant artifacts.
3. If the tier is equal, compare specificity.
4. If specificity is similar, compare approval state and freshness.
5. If ambiguity remains, flag the issue instead of silently guessing.

## Special rules by artifact family

### Architecture artifacts

- `architecture-rules.md` should be treated as stronger than `architecture-review.md` when the issue is a concrete constraint
- `architecture-review.md` remains important for rationale and impact interpretation

### Planning artifacts

- `delivery-structure.md` defines initiative planning structure but should not override active implementation contracts
- `traceability-matrix.md` supports linkage and validation but should not redefine approved engineering scope by itself

### Readiness and quality-gate artifacts

- readiness can determine whether work should proceed
- required quality-gate outputs can constrain or block downstream work
- these should outrank planning convenience and optional design preference

### Handoff artifacts

- `tasks.md` defines the immediate implementation contract
- `design.md` or `delivery-spec.md` defines implementation boundaries and design intent
- if `tasks.md` and `design.md` appear inconsistent, the conflict should be surfaced rather than silently merged

### Perspective artifacts

- `gitlab-planning-view.md` or similar projections are convenience views
- they should never override source-of-truth planning, readiness, architecture, or implementation artifacts

## Packaging implications

This precedence model should influence context packaging in the following ways:

- authoritative artifacts should be clearly marked
- lower-tier context should not appear to be equally binding
- optional narrative context should be visually or structurally secondary to governing constraints
- conflicts should be surfaced before the agent is asked to execute

## Brownfield implications

For existing-system enhancement work, precedence should also consider:

- approved compatibility constraints
- existing-system-impact decisions
- operational stability requirements

These should not remain merely advisory when they affect regression risk or rollout safety.

## Non-goals

This model is not intended to:

- eliminate all judgment
- replace architecture review or readiness decisions
- treat all conflicts as automatically resolvable
- promote generic framework guidance above initiative decisions

## Success criteria

The precedence model will be useful when:

- the framework can state which artifact has authority for a given question
- conflicts between planning, architecture, readiness, and task artifacts can be resolved consistently
- task packaging can clearly label governing versus supporting context
- implementation prompts no longer flatten all artifacts into equal importance

## Example precedence summary

In simplified form, the framework should generally behave like this:

1. governing constraints
2. approved active-task or deliverable contracts
3. initiative-specific planning and interpretive artifacts
4. generic framework guidance and projections

This is a decision model, not a strict filename-only ranking. Specificity, approval state, and freshness still matter.

## Open questions for next iteration

These questions should be refined in later design work:

- which readiness outputs should be considered governing versus advisory?
- how should partial approvals affect precedence?
- how should multi-repository handoff contracts be ranked against initiative-level design artifacts?
- should some artifact families have explicit sub-precedence inside the same tier?
- how should unresolved conflicts be represented in workflow state?

## Recommended next step

The next design step after this spec should be to define context drift detection and freshness rules so that the precedence model can operate not only on authority, but also on current validity.
