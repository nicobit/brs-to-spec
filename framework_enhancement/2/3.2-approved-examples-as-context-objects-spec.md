# Approved Examples As Context Objects Spec

This document defines a first draft of the framework's model for using approved examples as first-class context objects.

Its purpose is to improve consistency and pattern transfer by allowing downstream AI consumers to learn from curated examples in addition to formal rules and templates.

## Objective

Define how the framework should treat selected examples as reusable context objects that can support:

- artifact generation
- task decomposition
- review quality
- implementation pattern alignment

## Problem statement

Rules, templates, and process guidance are necessary, but they do not always provide enough pattern-level clarity for AI-assisted work.

Examples often help with:

- expected structure
- level of detail
- strong-versus-weak output quality
- common mistakes to avoid

Without examples, the framework may remain precise but still produce uneven outputs.

## Scope

This spec applies to curated examples used to improve framework outcomes.

This spec does not:

- treat examples as governing artifacts
- replace initiative-specific source-of-truth context
- define storage or tooling mechanisms yet

It defines the operating model for example usage.

## Core principle

Examples should teach patterns, not override truth.

Examples are useful when they clarify how to apply the framework, but they should remain subordinate to:

- initiative-specific approved artifacts
- governing constraints
- active task contracts

## Example categories

The framework should support examples such as:

### 1. Strong artifact examples

Examples of high-quality:

- business-intake summaries
- delivery-structure slices
- handoff artifacts
- design sections
- task breakdowns

### 2. Comparison examples

Examples showing:

- weak versus strong task decomposition
- weak versus strong design articulation
- overbroad versus well-scoped handoff packages

### 3. Pattern examples

Examples of recurring structures such as:

- brownfield enhancement decomposition
- governed-boundary handling
- validation-plan structure

### 4. Anti-pattern examples

Examples of outputs that should not be repeated, such as:

- task packages with excessive narrative overload
- missing constraints in design
- planning views mistaken for engineering contracts

## Usage rule

Examples should be included when they materially improve the likelihood of a better output.

They should be especially useful when:

- the output form is non-trivial
- the task requires a specific quality bar
- repeated quality inconsistency has been observed

Examples should not be included by default for every task.

## Relationship to suitability

Examples can improve context suitability by:

- reducing ambiguity
- setting an expected detail level
- showing what good looks like

However, examples should remain selective so they do not crowd out the initiative's actual context.

## Relationship to packaging and retrieval

Examples should be treated as optional supporting context unless explicitly elevated by later policy.

That means:

- retrieval should include them only when useful
- packaging should clearly distinguish them from governing artifacts

## Success criteria

This model will be useful when:

- generated artifacts become more consistent in quality and structure
- users and AI agents can learn from strong patterns directly
- framework outputs require less iterative correction for common structural issues

## Open questions for next iteration

- which example categories should be curated first?
- how should examples be selected without overfitting outputs to a single style?
- how should examples be tagged by task type, role, and delivery mode?

## Recommended next step

The next design step after this spec should be to define the framework feedback loop so that new examples can be added based on recurring delivery outcomes, not only initial curation.
