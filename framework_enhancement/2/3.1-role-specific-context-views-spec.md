# Role-Specific Context Views Spec

This document defines a first draft of the framework's model for role-specific context views.

Its purpose is to make the same source-of-truth initiative context easier to consume by reshaping it for different downstream roles without creating duplicated or competing truth sources.

## Objective

Define how the framework should project existing context into role-appropriate views for different consumers such as:

- product owners
- architects
- coding agents
- reviewers
- governance or release stakeholders

## Problem statement

The framework already distinguishes artifact consumers, but context is still largely organized around artifacts rather than around the decision needs of each role.

This can create:

- unnecessary detail for some consumers
- missing emphasis for others
- repeated manual reinterpretation of the same material

## Scope

This spec applies to consumer-facing context projections derived from existing framework artifacts.

This spec does not:

- create new source-of-truth artifacts
- replace packaging, retrieval, or precedence rules
- define specific UI or tooling implementations

It defines the projection model only.

## Core principle

One initiative may need many views, but it should still have one source of truth.

Role-specific views should therefore be projections, not forks.

## Role-view model

Each role-specific view should define:

- primary decisions supported
- primary context to emphasize
- context to downplay or omit by default
- authority cues that remain visible

## Suggested core roles

### Product owner view

Emphasize:

- business scope
- acceptance intent
- delivery boundaries
- readiness decision summary

Downplay:

- low-level implementation detail
- dense architecture constraint listings unless decision-relevant

### Architect view

Emphasize:

- architecture review
- architecture rules
- impacted boundaries and contracts
- existing-system impact
- relevant readiness and gate constraints

Downplay:

- broad business narrative without architectural consequence

### Coding-agent view

Emphasize:

- active implementation contract
- governing constraints
- focused design or delivery-spec sections
- acceptance criteria relevant to the task
- brownfield implementation reality where applicable

Downplay:

- broad planning hierarchy
- narrative context not tied to execution

### Reviewer view

Emphasize:

- active task contract
- implementation evidence or findings
- acceptance source
- architecture and gate constraints relevant to review scope

Downplay:

- unrelated planning or delivery structure detail

### Governance or release view

Emphasize:

- readiness decision
- required quality-gate outcomes
- rollout or validation constraints
- residual risks

Downplay:

- detailed implementation internals unless gate-relevant

## Relationship to retrieval and packaging

Role-specific views should not replace retrieval or packaging.

Instead:

- retrieval decides what context is selected
- packaging decides how it is structured
- role-specific views decide how emphasis and presentation should differ for the consumer

## Relationship to precedence

Role-specific views must preserve authority ordering.

They may change emphasis, but they should not blur which context is governing versus supporting.

## Success criteria

This model will be useful when:

- each major role can consume framework context with less manual reinterpretation
- the same initiative is easier to navigate across stakeholders
- role-specific AI interactions become more consistent

## Open questions for next iteration

- which role views should be defined first?
- how different should views be before they create duplication risk?
- how should views expose preserved nuance from Wave 2?

## Recommended next step

The next design step after this spec should be to define how approved examples can complement these role-specific views as reusable pattern guidance.
