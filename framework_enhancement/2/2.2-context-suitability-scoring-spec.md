# Context Suitability Scoring Spec

This document defines a first draft of the framework's context suitability scoring model.

Its purpose is to assess whether a context package is not only governed and complete, but also appropriately shaped for AI-assisted consumption.

## Objective

Define a lightweight scoring model that helps the framework determine whether a task or handoff context package is usable, clear, and appropriately bounded for downstream AI work.

## Problem statement

A context package can be formally approved and still be a weak AI input.

Common problems include:

- overly broad scope
- unclear boundaries
- excessive narrative density
- insufficient examples
- weak expression of constraints

The framework already governs readiness and artifact quality. This spec introduces an additional lens focused on AI usability.

## Scope

This spec applies to:

- implementation task packages
- review task packages
- handoff packages
- focused artifact-generation packages

This spec does not replace:

- readiness decisions
- quality-gate outcomes
- artifact precedence rules

It adds an AI-consumption quality lens only.

## Core principle

Good context is not just complete. It is also consumable.

A context package should be considered stronger when it is:

- specific
- bounded
- authoritative
- fresh
- high signal

## Suggested scoring dimensions

The framework should assess context suitability across at least these dimensions.

### 1. Scope sharpness

Question:

- is the active task or deliverable narrow enough to be executed confidently?

### 2. Constraint clarity

Question:

- are the governing rules, boundaries, and non-negotiable constraints explicit?

### 3. Acceptance clarity

Question:

- is success clear enough for the AI consumer to target the right outcome?

### 4. Context relevance

Question:

- does the package mostly contain directly useful material rather than broad background?

### 5. Context density

Question:

- is the package concise enough to remain high signal?

### 6. Freshness confidence

Question:

- is the package likely current, or does it contain review-needed or stale dependencies?

### 7. Example support

Question:

- where the task is non-obvious, does the package include examples, patterns, or comparable references?

## Suggested scoring scale

Each dimension can later be evaluated using a simple qualitative scale such as:

- strong
- adequate
- weak

Or, if preferred later:

- 3
- 2
- 1

This spec does not require a numeric model yet. The important thing is consistent interpretation.

## Suggested interpretation model

### Strong suitability

The package is likely safe and efficient for AI-assisted execution.

Typical characteristics:

- narrow scope
- clear constraints
- fresh inputs
- little irrelevant context

### Adequate suitability

The package is probably usable but may benefit from refinement.

Typical characteristics:

- generally clear scope
- minor ambiguity
- some low-value context
- moderate reliance on interpretation

### Weak suitability

The package is likely to create poor AI output or execution risk unless improved first.

Typical characteristics:

- ambiguous scope
- missing constraints
- weak acceptance definition
- stale or uncertain freshness
- excessive narrative overload

## Usage rule

Context suitability scoring should be advisory but meaningful.

It should help answer:

- should we proceed as-is?
- should we tighten the context first?
- is the package approved but not yet AI-ready?

## Relationship to readiness

Readiness and suitability are related but different.

- readiness asks whether work is allowed to proceed in governance terms
- suitability asks whether the context is well-shaped for AI execution

A package may be:

- ready but weakly suitable
- suitable but not ready
- both ready and suitable

The framework should keep those distinctions visible.

## Relationship to packaging and retrieval

Suitability scoring should evaluate the result of:

- retrieval choices
- packaging choices
- precedence clarity
- freshness state

It is not a substitute for those models. It is a quality check over their outcome.

## Suggested improvement triggers

If suitability is weak, the framework should later be able to recommend improvements such as:

- narrow the active scope
- remove unrelated context
- elevate authoritative constraints more clearly
- add acceptance examples
- confirm freshness of dependencies

## Success criteria

This model will be useful when:

- users can distinguish approved context from AI-ready context
- weak packages are identified before implementation begins
- context refinement becomes more systematic
- downstream AI execution becomes more predictable

## Open questions for next iteration

- should the scoring model be qualitative or numeric first?
- which dimensions should be mandatory at first rollout?
- what score should trigger rework versus warning-only?
- how should suitability be summarized in handoff artifacts?

## Recommended next step

The next design step after this spec should be to define context-loss controls across stage transitions so the framework can protect the kinds of nuance that often drive suitability quality.
