# Final Plan - Prompt Placeholder Support

## Goal

Implement workflow-driven prompt placeholders so `.b2s` prompts can use
engine-resolved input and output paths without hardcoding filesystem paths in
skill text.

## Why this change

Today:

- workflow actions declare input patterns and outputs
- Python resolves which files exist
- prompts still hardcode path-reading instructions

This creates drift risk between:

- workflow contract
- engine resolution
- prompt instructions

The new design keeps the current staged model but adds a prompt-facing contract
generated by the engine.

## Final placeholder set

- `{required_inputs}`
- `{optional_inputs}`
- `{resolved_required_inputs}`
- `{resolved_optional_inputs}`
- `{primary_output}`
- `{secondary_outputs}`

## Implementation strategy

1. Extend `collect-inputs` so it produces a prompt-facing placeholder object in
   addition to the current diagnostic structure.
2. Derive output placeholders from the selected action during the same phase so
   prompts get a single resolved contract.
3. Add a lightweight placeholder-rendering step to workflow execution.
4. Update the orchestration prompt and a small number of representative skill
   prompts to use the new placeholders.
5. Add test coverage for placeholder generation and prompt rendering.
6. Document the contract and migration rules.

## Design rules

1. Do not expose `matches` in prompt-facing placeholder names.
2. Keep diagnostic data and prompt-facing data separate.
3. Render list placeholders as structured lists, not comma-separated strings.
4. Keep placeholder names generic across workflow types.
5. Start with incremental prompt migration, not a repo-wide rewrite.

## Recommended first migration targets

Use these as the first representative prompts:

- `.b2s/prompts/run-workflow.md`
- one wildcard-heavy skill such as `create-business-intake-summary`
- one planning skill such as `create-delivery-structure`

These give coverage for:

- fixed required inputs
- wildcard optional inputs
- directory inputs
- single primary output

## Expected result

After implementation:

- engine remains the source of resolved path truth
- prompts consume a stable placeholder contract
- workflow types can vary input paths without forcing prompt rewrites
- hardcoded path instructions are reduced
