## Acceptance Criteria

### AC-001 — UI displays score `[ui]`

```gherkin
Scenario: Show score and recommendation in applicant view
  Given an applicant has a `application.scored` event
  When a support user views the application
  Then the UI shows the latest score and human-readable recommendation and a link to explainability metadata
```

### AC-002 — Missing score handled `[ui]`

```gherkin
Scenario: Score missing or delayed
  Given no `application.scored` event is available
  When a support user views the application
  Then the UI shows "Score pending" and a link to audit logs for investigators
```

### AC-003 — Auto-decline notification & cooling-off `[integration]`

```gherkin
Scenario: Auto-decline handling and notification
  Given an `application.scored` event with recommendation = AUTO_DECLINE
  When the system processes the scored event
  Then a decline notification is sent to the applicant within 5 minutes and the UI shows cooling-off information per policy
```

---

## Business Context

This story ensures applicant-facing visibility and regulatory traceability for scoring outcomes, improving support response and compliance posture.

## Implementation Guidance

The frontend should consume the `application.scored` event or read from the canonical application read model. Ensure explainability metadata (REQ-024) and audit references are shown in the UI. Keep the display read-only and reference the durable audit store for full records.
