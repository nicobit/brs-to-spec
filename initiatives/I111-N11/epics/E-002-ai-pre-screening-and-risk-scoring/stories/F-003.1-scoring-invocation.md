## Acceptance Criteria

### AC-001 — Scoring produced `[integration]`

```gherkin
Scenario: Invoke scoring on application submission
  Given an `application.submitted` event
  When the scoring service processes the event
  Then a `application.scored` event is emitted with score and recommendation
```

### AC-002 — Recommendation semantics `[unit]`

```gherkin
Scenario: Recommendation values defined
  Given scoring logic runs
  Then the recommendation is one of AUTO_APPROVE, REFER_TO_UNDERWRITER, AUTO_DECLINE
```

### AC-003 — Trigger within SLA `[integration]`

```gherkin
Scenario: Pre-screening triggered within SLA
  Given an application submission event (ARN assigned)
  When the submission is processed
  Then the AI pre-screening is triggered within 60 seconds
```

## Business Context

This story provides the programmable scoring contract enabling automated decisions and risk triage. It is valuable because it reduces manual underwriting load and speeds decisioning for low-risk applicants.

## Implementation Guidance

Refer to the implementation contract at `implementation-contract.md` for the `application` entity, `/api/v1/score` API, and `application.scored` event. Ensure the service emits `application.scored` with `score:int` and `recommendation:string` fields matching the canonical schema. Implement idempotency for event processing and include correlation IDs.
