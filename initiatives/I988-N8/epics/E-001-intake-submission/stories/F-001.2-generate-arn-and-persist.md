## User Story

As a **system**, when a valid application is submitted, I generate a stable ARN and persist the application so downstream services can reference the ARN.

---

## Business Context

ARN is the canonical identifier used across scoring, compliance, and disbursement flows.

---

## Linked Requirements

- REQ-001, REQ-002, FR-004, FR-005

---

## Implementation Guidance

- Implement idempotent ARN generation (use hash of canonicalised payload + timestamp window) and store in `applications` table. Emit `application.submitted` event to event bus.

---

## Acceptance Criteria

### AC-001 — Persist and emit `[integration]`

```gherkin
Scenario: Persist application and publish event
  Given a valid application payload
  When the backend creates the application
  Then the application record exists in the DB with a unique ARN and an application.submitted event is published
```

### AC-002 — Idempotency `[unit]`

```gherkin
Scenario: Duplicate submission returns same ARN
  Given the same request payload is submitted twice
  When the second submission occurs within the idempotency window
  Then the service returns the same ARN and does not create a duplicate record
```
