## User Story

As the Compliance Service, I want to orchestrate AML/KYC screenings for every submitted application ARN, so that screening results are recorded and appropriate downstream routing (auto-block, create task) occurs.

---

## Business Context

Automated screening reduces manual workload, surfaces high-risk cases quickly, and provides the audit trail regulators require. This story implements the orchestration and integration points to run provider checks and persist the canonical screening record.

## Implementation Guidance

- **Entity:** `SCREENINGS` in `implementation-contract.md`
- **API:** `POST /api/v1/compliance/aml-screenings`
- **Status:** screening record created in `SCREENINGS` with `result` pending -> PASS/REVIEW/BLOCK
- **Events:** emits `screening.completed` and `audit.event`
- **Rules:** BR-003/BR-004 govern downstream routing

---

## Acceptance Criteria

### AC-001 — Happy path `[integration]`
```gherkin
Scenario: Screening completes PASS for a low-risk ARN
  Given an application exists with arn "ARN-ABC12345"
  When the Compliance Service requests screening for that arn
  Then a SCREENINGS record is created with result "PASS"
  And a `screening.completed` event is emitted containing id, arn, result, and screened_at
```

### AC-002 — Provider failure fallback `[integration]`
```gherkin
Scenario: External provider times out
  Given an external provider times out
  When screening is attempted
  Then the system marks screening as REVIEW and creates an underwriter task with priority MEDIUM
  And an `audit.event` is emitted indicating the provider timeout and correlation id
```

### AC-003 — Blocking rule `[unit]`
```gherkin
Scenario: Screening returns BLOCK
  Given screening result is BLOCK with reason_code "SANCTION_HIT"
  When the result is processed
  Then the application status is set to BLOCKED
  And an escalation underwriter task is created with priority HIGH
```
