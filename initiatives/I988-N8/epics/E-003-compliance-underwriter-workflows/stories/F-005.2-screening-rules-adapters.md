## User Story

As a Compliance Engineer, I want provider adapters and deterministic rule mappings so screening results are consistent and traceable.

---

## Business Context

Standardising adapter behaviour and mapping ensures the same provider outputs produce consistent PASS/REVIEW/BLOCK decisions and supports auditability.

## Implementation Guidance

- Adapter layer must normalize provider fields into canonical screening structure stored in `SCREENINGS.details`.
- Redaction policy applied before storage; store hash of raw payload if required by forensics.

---

## Acceptance Criteria

### AC-001 — Normalisation `[unit]`
```gherkin
Scenario: Provider payload normalised
  Given Experian returns provider-specific fields
  When adapter processes payload
  Then the system stores canonical fields in SCREENINGS.details and a normalized result
```

### AC-002 — Redaction and storage validation `[integration]`
```gherkin
Scenario: Provider payload contains PII and redaction policy applies
  Given provider payload contains PII fields
  When adapter processes and stores the payload
  Then stored `details` are redacted per policy and a retention-hash is recorded
```
