# S-001.1 — Implement Intake API POST /applications

| Story ID | S-001.1 |
|---|---|
| Layers | Backend / Backend API |

| Story Type | backend-endpoint |

## User Story

As an intake API developer, I want a POST `/api/v1/applications` endpoint that accepts application payloads, validates them, persists an application record, and emits `application.submitted` so downstream systems can consume the application event.

## Business Context

This is the primary entrypoint for new customers and must be reliable and auditable; it maps directly to acceptance criteria required by FR-001 and FR-002.

## Requirements Implemented

- FR-001
- FR-002
- NFR-001

## Requirements Referenced

- FR-003 (identity check via Experian)

## In Scope

- Validate request payload, persist application record, emit domain event `application.submitted`.

## Implementation Guidance

Refer to `implementation-contract.md` for payload schema. Use repository pattern and domain events. Ensure idempotency handling for duplicate submissions.

## Test Expectations

- Unit tests for validation and persistence mapping
- Integration test verifying event emission
- Contract test for API surface

## Required Tests

- 2 unit tests
- 1 integration test

## Acceptance Criteria (Gherkin)

AC Tags: [critical] [automate]

```gherkin
@critical @automate
Scenario: Happy path - submit application
	Given a valid application payload
	When POST /api/v1/applications is called
	Then response is 201 and an application ARN is returned
	And an `application.submitted` event is emitted

@critical @automate
Scenario: Validation failure - missing required field
	Given an application payload missing required fields
	When POST /api/v1/applications is called
	Then response is 400 with validation errors

@critical @automate
Scenario: Idempotency - duplicate submission
	Given the same idempotency-key is used twice
	When POST /api/v1/applications is called twice
	Then the second call returns 200/202 and does not create a duplicate record

@important @automate-later
Scenario: Integration - scoring pipeline receives event
	Given an application is submitted and event emitted
	When the scoring pipeline consumes `application.submitted`
	Then the scoring service receives the expected payload and creates a scoring job
```

*End of story.*
