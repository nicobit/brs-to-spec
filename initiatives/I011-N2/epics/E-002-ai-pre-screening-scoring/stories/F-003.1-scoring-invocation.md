# F-003.1 — Scoring Invocation and Orchestration

| Field | Value |
|---|---|
| Layers | Backend, Frontend, Infrastructure, Integration |
| Story ID | F-003.1 |

## Business Context

When an application is submitted (ARN assigned), the system must invoke the AI scoring pipeline to produce a risk score and recommendation. Fast automated scoring reduces manual triage and improves throughput.

## Linked Requirements

- REQ-004 — AI Pre-Screening Trigger and Output
- REQ-012 — Performance and Scalability NFRs

## User Story

As a Loan Origination system, I want the scoring service invoked reliably for every submitted ARN so that decisions are produced automatically and within SLA.

## Implementation Guidance

- The Loan Origination API emits a scoring event to the Scoring Service with ARN and required payload.
- Use a resilient message bus (Azure Service Bus) and idempotent invocation to ensure retries do not double-score.
- Apply circuit-breaker for downstream integrations (Experian) and model endpoint.

### Event contract (example)

```json
{
	"eventType": "ApplicationSubmitted.v1",
	"arn": "ARN-000000",
	"correlationId": "<guid>",
	"payload": {
		"applicant": { "id": "<id>", "dob": "YYYY-MM-DD" },
		"applicationData": { /* minimal data required by model */ }
	},
	"idempotencyKey": "<arn|submission-timestamp|hash>"
}
```

### Idempotency and deduplication

- Persist an `idempotencyKey` per ARN (or use `correlationId`) to ensure repeated events do not create duplicate scores. Message handler should be idempotent and return the existing score when seen again.
- Use Service Bus message lock + peek-lock processing and move poison messages to DLQ after N retries.

### Retry, circuit-breaker & fallback

- Retry model calls with exponential backoff (max total latency budget <=90s). Use a short-circuit (circuit breaker) on repeated failures of the model or Experian.
- On timeout or repeated model failures: write an audit entry and set recommendation `REFER_TO_UNDERWRITER`.

### Observability & monitoring

- Emit metrics: `scoring.duration`, `scoring.success_count`, `scoring.failure_count`, `scoring.timeout_count`, and `scoring.retries`.
- Log correlationId and idempotencyKey for traceability. Alert on elevated `scoring.timeout_count` or circuit-breaker open rate.

### Test notes

- Integration tests should publish `ApplicationSubmitted.v1` and assert a score persisted, recommended label, timing (<90s), and DLQ/fallback behaviour on simulated model unavailability.

## Acceptance Criteria (Gherkin)

```gherkin
@integration @happy
Scenario: Scoring completes successfully within SLA
	Given a valid application submission with ARN and required data
	When the scoring pipeline is invoked
	Then a risk score between 0 and 1000 and a recommendation label (AUTO_APPROVE|REFER_TO_UNDERWRITER|AUTO_DECLINE) shall be recorded within 90 seconds

@integration @negative
Scenario: Scoring times out or model unavailable
	Given a valid application submission
	When the scoring pipeline cannot produce a result within 90 seconds
	Then the application shall be routed to REFER_TO_UNDERWRITER and an audit entry shall record the timeout
```

## Test Expectations

- Integration tests that simulate submission and assert scoring result, timing, and fallback routing.
