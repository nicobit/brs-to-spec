# Retrieval Guidance By Task Type, Role, And Delivery Mode Spec

This document defines a first draft of the framework's retrieval guidance model for downstream AI-assisted work.

Its purpose is to determine what context should be loaded, in what form, and with what priority for a given task, role, and delivery mode.

## Objective

Define how the framework should select context for downstream work so that:

- the right context is loaded for the active task
- high-value sections are preferred over whole-document overload
- different roles receive context appropriate to their purpose
- delivery mode and initiative type influence what is retrieved

This spec complements the per-task context packaging model, the artifact precedence model, and the context freshness model by defining how context should actually be selected for use.

## Problem statement

The framework already defines which artifacts should exist and why they matter. However, a context-driven framework must go further and define which parts of those artifacts should be loaded for a specific action.

Without retrieval guidance, downstream prompts risk becoming:

- too broad
- too generic
- role-inappropriate
- overloaded with entire documents instead of focused sections

This can reduce AI effectiveness even when the underlying artifacts are high quality.

## Scope

This spec applies to context retrieval for:

- implementation tasks
- review or fix tasks
- handoff-generation tasks
- readiness-support or architecture-sensitive tasks
- role-specific downstream consumption

This spec does not yet define:

- technical retrieval implementation
- indexing or search behavior
- tooling integration details
- automated summarization rules

It defines the framework selection model only.

## Core principle

Context retrieval should be demand-shaped, not inventory-shaped.

That means the framework should not load context simply because it exists. It should load context because it is the best available support for the active task and role.

## Retrieval dimensions

Retrieval decisions should be shaped by at least these dimensions:

- task type
- role
- delivery mode
- initiative mode or risk profile
- artifact authority
- freshness state
- context granularity

## Retrieval hierarchy

The framework should retrieve context in this general order:

1. active task contract
2. governing constraints
3. active design or delivery-definition context
4. minimum necessary supporting context
5. optional enrichment only when it materially improves execution quality

This order should help keep prompts focused and authority-aware.

## Task-type retrieval guidance

### 1. Implementation task retrieval

Primary objective:

- implement one approved engineering task safely and correctly

Default retrieval priority:

1. active task definition
2. relevant `design.md` or `delivery-spec.md` sections
3. relevant architecture rules
4. required quality-gate outputs
5. active acceptance-related sections
6. brownfield impact context when relevant
7. limited planning context only when needed for traceability or dependency clarity

Default exclusions:

- unrelated stories or deliverables
- broad business narrative not tied to the task
- full planning documents when only one section is needed
- optional visuals without direct task value

### 2. Review or fix task retrieval

Primary objective:

- assess or correct a specific implemented unit against approved expectations

Default retrieval priority:

1. active task definition
2. relevant design or delivery-spec sections
3. review findings, defect detail, or failure evidence
4. architecture rules and relevant gate constraints
5. acceptance source sections tied to the issue
6. supporting rationale only when it helps interpret intent

Default exclusions:

- broad planning context
- unrelated requirement detail
- full business-intake narrative unless the issue concerns intent mismatch

### 3. Handoff-generation retrieval

Primary objective:

- produce an implementation-ready contract for one active deliverable

Default retrieval priority:

1. active delivery-structure scope
2. architecture review and architecture rules
3. readiness decision
4. triggered quality-gate outputs
5. traceability inputs where applicable
6. business-intake summary sections that clarify business intent
7. optional focused diagrams when they improve clarity

Default exclusions:

- inactive slices
- alternative planning paths that were not selected
- generic framework guidance once initiative-specific direction exists

### 4. Architecture-sensitive review retrieval

Primary objective:

- assess whether a planned or implemented change respects architecture boundaries and constraints

Default retrieval priority:

1. architecture rules
2. relevant architecture review sections
3. active task or design sections
4. required gate outputs related to boundary, contract, or integration implications
5. existing-system-impact context when brownfield

Default exclusions:

- unrelated business narrative
- detailed planning hierarchy not relevant to the impacted boundary

## Role-based retrieval guidance

### Product owner or business review role

Retrieve primarily:

- business-intake summary
- active delivery-structure scope
- readiness summary where decision-relevant
- acceptance and business-boundary context

Avoid default retrieval of:

- low-level implementation-task detail
- broad architecture rule sets unless directly relevant to a decision

### Architect or tech-lead role

Retrieve primarily:

- architecture review
- architecture rules
- active deliverable definition
- existing-system-impact context
- relevant planning structure and quality-gate outputs

Avoid default retrieval of:

- unnecessary broad business narrative
- unrelated implementation task detail

### Coding-agent role

Retrieve primarily:

- approved active task contract
- relevant design or delivery-spec sections
- governing architecture and gate constraints
- focused acceptance context
- brownfield implementation context where relevant

Avoid default retrieval of:

- whole-initiative planning sets
- planning projections
- business narrative beyond task-relevant intent

### Reviewer role

Retrieve primarily:

- active task contract
- design or delivery-spec sections
- implementation evidence or review findings
- acceptance source
- architecture and quality constraints relevant to review scope

Avoid default retrieval of:

- generalized planning context unless needed to resolve scope ambiguity

### Governance or release role

Retrieve primarily:

- readiness decision
- required quality-gate outputs
- architecture constraints affecting release or rollout
- validation evidence summaries

Avoid default retrieval of:

- low-level implementation detail unless a gate specifically requires it

## Delivery-mode retrieval guidance

### OpenSpec mode

Emphasize retrieval from:

- `openspec/changes/.../tasks.md`
- `openspec/changes/.../design.md`
- relevant `specs/` material
- governing upstream architecture and gate artifacts

De-emphasize:

- initiative-wide planning context once the active OpenSpec story package is sufficiently defined

### Standalone mode

Emphasize retrieval from:

- `delivery-spec.md`
- `tasks.md`
- `validation-plan.md`
- readiness and gate artifacts
- architecture review and architecture rules

De-emphasize:

- planning projections
- broad initiative documentation outside the active deliverable

### Business Copilot or business-review mode

Emphasize retrieval from:

- business-intake outputs
- planning scope summaries
- readiness summaries
- business-facing visuals when helpful

De-emphasize:

- low-level engineering contracts unless the audience is explicitly crossing into engineering review

## Initiative-mode and risk-aware retrieval guidance

### Greenfield or BRS-first

Default retrieval can rely more heavily on:

- business-intake context
- architecture review
- planning and design artifacts

### Brownfield or existing-system enhancement

Default retrieval should elevate:

- existing-system-impact context
- compatibility and regression constraints
- architecture rules related to stability and boundaries
- operationally sensitive design or rollout context

### Small change or fast path

Default retrieval should stay narrow:

- active task
- relevant design or delivery-spec sections
- direct constraints only

Do not pull broad initiative context unless required by risk or ambiguity.

### High-risk or governed-boundary work

Default retrieval should elevate:

- architecture rules
- required quality-gate outputs
- boundary or contract definitions
- traceability and acceptance evidence where relevant

## Freshness rule for retrieval

Retrieval should prefer fresh context and avoid silently loading stale authoritative context.

Rules:

- stale authoritative context should not be treated as execution-ready
- review-needed context may be loaded only with visible caution
- freshness should be checked before broad optional enrichment is added

## Granularity rule for retrieval

The default retrieval unit should be the smallest useful scope.

Preferred order:

1. section
2. subsection
3. focused excerpt
4. whole document only when naturally narrow

Retrieval should avoid full-document loading when a section-level selection is sufficient.

## Visual retrieval rule

Diagrams or other visual context should be retrieved only when they materially improve understanding of:

- system boundaries
- sequence flow
- integration behavior
- dependency or interaction structure

If text is already sufficient, visuals should not be loaded by default.

## Retrieval profiles concept

The framework should later define reusable retrieval profiles combining:

- task type
- role
- delivery mode
- risk pattern

Examples:

- OpenSpec implementation profile
- standalone review profile
- brownfield implementation profile
- architecture gate profile
- small-change fast-path profile

These profiles would make retrieval more consistent without requiring ad hoc context selection every time.

## Packaging implications

Retrieval is the input-selection layer for packaging.

That means:

- retrieval decides what candidate context is brought forward
- packaging decides how that context is arranged into required, authoritative, optional, and excluded layers

Retrieval should therefore remain selective and authority-aware.

## Precedence implications

Retrieval should not flatten artifact authority.

If lower-tier context is retrieved for clarity, it should still remain subordinate to higher-tier governing sources.

## Non-goals

This model is not intended to:

- retrieve every available artifact by default
- make all roles consume the same context
- treat whole-document loading as the default safe behavior
- promote convenience projections over source-of-truth artifacts

## Success criteria

The retrieval model will be useful when:

- each major task type has a clear default retrieval pattern
- each major role has a context shape appropriate to its decisions
- delivery mode changes retrieval behavior in sensible ways
- low-value and unrelated context is reduced
- prompts become more focused without losing critical constraints

## Open questions for next iteration

These questions should be refined in later design work:

- what exact retrieval profiles should exist first?
- how should retrieval behave under strict context-window constraints?
- which artifacts should have section-level retrieval guidance defined explicitly?
- how should visuals be referenced versus embedded?
- when should retrieval escalate from narrow to expanded context automatically?

## Recommended next step

With packaging, precedence, freshness, and retrieval now defined at a first-draft level, the next useful step would be to produce a Wave 1 synthesis document that unifies the four models into one coherent context-driven operating layer for the framework.
