# Per-Task Context Packaging Model Spec

This document defines a first draft of the framework's per-task context packaging model.

Its purpose is to make context delivery to AI consumers deliberate, consistent, and bounded. The model is intended to improve task execution quality without changing the current role of existing framework artifacts.

## Objective

Define how the framework should assemble the context bundle for one focused downstream activity such as:

- implementing one approved engineering task
- reviewing one implemented task
- generating one handoff artifact
- validating one architecture-sensitive change

The packaging model should ensure that the AI consumer receives:

- the minimum required context
- the highest-authority context
- the most relevant supporting context
- clear exclusions for low-value or distracting context

## Problem statement

The framework already produces strong artifacts, but it does not yet define a standard method for selecting and packaging the exact subset of those artifacts for one unit of AI-assisted work.

Without a packaging model, the downstream prompt may:

- include too much context
- omit mandatory constraints
- mix authoritative and non-authoritative material
- overload the agent with whole-document context when only selected sections are needed

This creates risk even when the framework's upstream artifacts are complete and well-governed.

## Scope

This spec applies to downstream AI-consumed work units, especially:

- coding-agent implementation tasks
- coding-agent fix tasks
- post-implementation review tasks
- focused design or handoff generation tasks

This spec does not yet define:

- the technical implementation of packaging
- automation behavior
- file format changes
- prompt syntax details

It defines the operating model and decision rules only.

## Core principle

The packaging model should be task-centered, not artifact-centered.

That means the framework should not ask:

"What documents exist for this initiative?"

It should ask:

"What exact context is required for this specific downstream task to be completed safely and correctly?"

## Packaging model structure

Each task context package should be assembled using four layers:

1. required context
2. authoritative constraints
3. optional supporting context
4. excluded context

### 1. Required context

This is the minimum context without which the task should not proceed.

Examples:

- the approved task definition
- active acceptance source relevant to the task
- initiative-specific architecture constraints that affect the task
- required quality-gate outputs when they constrain implementation or review

Rules:

- required context must be present
- if required context is missing, the task should be considered not ready for AI execution
- required context should be task-specific, not initiative-global by default

### 2. Authoritative constraints

This is the context that defines what the AI must obey when there is ambiguity or tension.

Examples:

- architecture rules
- quality-gate decisions
- approved interface or data-boundary constraints
- current readiness constraints that remain active at implementation time

Rules:

- authoritative constraints override optional or narrative context
- authoritative constraints must be explicitly identified in the package
- when a task is architecture-sensitive or boundary-sensitive, these constraints must be elevated prominently

### 3. Optional supporting context

This is useful context that improves correctness or efficiency, but is not the controlling source of truth.

Examples:

- business-intake excerpts for business intent
- planning context for broader story placement
- relevant design rationale
- existing-system-impact context for brownfield awareness
- focused diagrams when they materially improve clarity

Rules:

- optional context should be included only when it adds likely value to the task
- optional context should be section-scoped where possible
- optional context should not crowd out required or authoritative context

### 4. Excluded context

This is context that exists in the framework but should not be loaded for the current task unless a specific reason arises.

Examples:

- unrelated user stories
- broad initiative narrative with no task relevance
- stale artifact versions
- duplicate summaries of already included authoritative material
- optional visuals that do not improve understanding

Rules:

- excluded context should remain accessible, but not part of the default task bundle
- exclusion is an intentional quality rule, not a sign that the source artifact lacks value

## Packaging decision flow

For each task, the framework should determine context in this order:

1. Identify the task unit.
2. Identify the task type.
3. Identify the minimum required context.
4. Identify governing constraints that have higher authority than narrative context.
5. Add optional context only if it improves task safety, clarity, or efficiency.
6. Remove low-value, duplicate, or unrelated context.
7. Confirm that the final package is fresh enough for use.

## Task types covered by the model

The packaging model should support at least these task classes:

- implementation task
- review/fix task
- architecture review task
- handoff generation task
- readiness or gate-support task

Each task class should later have a packaging profile.

## Proposed packaging profiles

### Implementation task profile

Primary goal:

- implement one approved task safely and correctly

Typical required context:

- approved `tasks.md` item or equivalent implementation contract
- relevant `design.md` or `delivery-spec.md` sections
- active acceptance criteria or acceptance source excerpts
- relevant architecture rules
- required quality-gate constraints

Typical optional context:

- focused business-intake summary excerpt
- delivery-structure context for traceability
- brownfield impact excerpt
- supporting diagram excerpt if directly helpful

Typical exclusions:

- unrelated stories
- broad planning detail outside the active task
- repeated summaries of architecture constraints already included

### Review or fix task profile

Primary goal:

- assess or correct an implemented unit against approved expectations

Typical required context:

- implementation task definition
- relevant design or delivery-spec sections
- review findings or defect details
- authoritative architecture and quality constraints

Typical optional context:

- business rationale excerpt
- earlier assumptions or tradeoff notes

Typical exclusions:

- unrelated readiness or planning detail
- broad initiative context not tied to the reviewed change

### Handoff generation task profile

Primary goal:

- generate an implementation-ready handoff artifact for one active deliverable

Typical required context:

- approved delivery structure for the active scope
- architecture review and rules
- readiness decision
- triggered quality-gate outputs
- traceability inputs when applicable

Typical optional context:

- business-intake summary excerpts
- visual aids where they clarify boundaries or interactions

Typical exclusions:

- stale planning alternatives
- inactive slices
- optional detail that does not improve implementation readiness

## Packaging dimensions

Every context package should be evaluated along these dimensions:

- relevance: does this context directly help the active task?
- authority: does this context constrain the task outcome?
- specificity: is this context specific to the current task?
- freshness: is this context still current?
- density: is the context concise enough to remain high signal?

These dimensions help distinguish useful context from merely available context.

## Freshness rule

The packaging model depends on freshness, even though detailed drift detection may be defined separately.

Minimum packaging rule:

- a package should identify whether any included artifact is potentially stale
- stale or possibly stale context should not be silently treated as current
- authoritative sources should be checked first for freshness risk

## Context granularity rule

The default unit of inclusion should be the smallest useful context slice, not the whole artifact.

Preferred order:

1. relevant section
2. relevant subsection
3. focused artifact excerpt
4. whole document only when the document is already narrow and task-specific

This helps reduce context-window waste and keeps prompts more precise.

## Brownfield rule

When the task affects an existing system, the package should include not only narrative project context but also the most relevant existing-system context available.

At minimum, brownfield packaging should consider:

- impacted component context
- compatibility or regression constraints
- boundary and contract implications
- operational or deployment sensitivity when known

This rule may later be expanded once live system context becomes a formal framework input.

## Visual context rule

Visuals should be included only when they materially improve understanding of:

- boundaries
- interactions
- data flow
- sequence-sensitive behavior

A diagram should not be included only because it exists.

If text is already sufficiently clear, the diagram should remain excluded from the default package.

## Proposed artifact roles in packaging

The model assumes four role types for source artifacts:

- source-of-truth artifact
- governing constraint artifact
- supporting context artifact
- reference-only artifact

This role assignment is packaging-relevant even if the underlying artifact structure stays unchanged.

## Non-goals

This model is not intended to:

- make every task consume every artifact
- replace readiness or quality gates
- collapse artifact distinctions into one large prompt
- turn optional context into mandatory context by default

## Success criteria

The packaging model will be considered useful when:

- the framework can define a standard context package for each major task type
- required context is distinguishable from optional context
- authoritative constraints are explicitly surfaced
- low-value context is intentionally excluded
- task prompts become narrower, clearer, and more reproducible

## Open questions for next iteration

These questions should be resolved in later design work:

- what exact packaging profiles should exist by delivery mode?
- how should packaging interact with small-change fast paths?
- how should packaging represent partial freshness risk?
- how should multi-repository handoff packages be context-partitioned?
- what context limits should be recommended for different downstream AI tasks?

## Recommended next step

The next design step after this spec should be to define:

1. artifact precedence and conflict-resolution rules
2. task-type packaging profiles in more detail
3. retrieval guidance by role and workflow step

Those items would turn this packaging model from a conceptual rule set into an operational framework behavior.
