# Feedback Loop From Implementation Outcomes Spec

This document defines a first draft of the framework's model for learning from downstream implementation outcomes and feeding that learning back into upstream framework refinement.

Its purpose is to help the framework improve over time based on repeated real delivery evidence rather than only on initial design intent.

## Objective

Define how the framework should detect recurring downstream issues and convert them into upstream improvement inputs for:

- prompts
- templates
- readiness guidance
- packaging rules
- architecture guidance

## Problem statement

Without a structured feedback loop, repeated downstream issues remain isolated to individual initiatives or delivery cycles.

This causes the framework to miss opportunities to learn from:

- recurring code review findings
- repeated task ambiguity
- recurring architecture exceptions
- repeated validation or test-pattern gaps
- recurring brownfield surprises

## Scope

This spec applies to framework-level learning from downstream implementation, review, and validation outcomes.

This spec does not yet define:

- analytics or telemetry implementation
- storage structure for findings
- formal governance workflow for framework updates

It defines the conceptual model only.

## Core principle

Repeated downstream friction should become upstream framework improvement input.

The framework should learn not only from planned intent, but also from observed delivery behavior.

## Feedback source categories

The framework should consider at least these categories of learning inputs.

### 1. Review findings

Examples:

- repeated senior-code-review corrections
- recurring QA review gaps
- repeated architecture-review concerns

### 2. Task-quality findings

Examples:

- recurring ambiguity in generated tasks
- repeated missing acceptance detail
- recurring overbroad or under-scoped task packages

### 3. Brownfield findings

Examples:

- recurring missed compatibility issues
- hidden dependency surprises
- repeated operational constraints discovered too late

### 4. Validation findings

Examples:

- recurring missing test expectations
- weak validation-plan patterns
- common release-readiness misses

## Actionability rule

Not every issue should trigger framework change.

A finding should become a framework refinement candidate when it is:

- repeated
- preventable through better framework guidance
- broad enough to matter beyond one isolated task

## Candidate refinement targets

When recurring issues are detected, likely refinement targets include:

- prompt instructions
- artifact templates
- readiness criteria
- packaging guidance
- retrieval guidance
- architecture review guidance
- example-library additions

## Relationship to examples

The feedback loop should help identify where new examples are needed.

For example:

- if weak task decomposition repeats, add strong-versus-weak decomposition examples
- if design outputs repeatedly miss boundary articulation, add a high-quality design example

## Relationship to Wave 1 and Wave 2

The feedback loop should improve:

- packaging quality
- precedence clarity
- freshness handling
- retrieval guidance
- brownfield grounding
- suitability quality
- transition-preservation quality

This makes Wave 3 the learning layer on top of Waves 1 and 2.

## Success criteria

This model will be useful when:

- repeated downstream issues become visible as reusable learning
- framework improvements can be traced back to observed delivery patterns
- prompts and templates improve in response to real usage
- repeated avoidable failure modes decrease over time

## Open questions for next iteration

- what threshold should define a recurring issue?
- how should findings be categorized across initiatives?
- who should approve framework refinements triggered by feedback?
- how should one-off local issues be filtered out?

## Recommended next step

With Wave 3 now outlined, the next useful step would be a cross-wave synthesis document showing how Waves 1, 2, and 3 together form a context-driven AI maturity model for the framework.
