# Wave 1 Enhancement Backlog

This backlog translates the Wave 1 roadmap into concrete enhancement items that can later be designed and implemented in the framework.

The focus of Wave 1 is to make the framework more explicitly context-driven at the point where AI-assisted work is actually performed.

## Wave 1 objective

Ensure that downstream AI consumers receive the right context, in the right form, with the right authority, and with visible freshness status.

## Backlog item 1: Per-task context packaging model

### Objective

Define how the framework assembles the context bundle for one implementation task, review task, or focused artifact-generation task.

### Problem being solved

The framework creates strong artifacts, but it is not yet explicit about what exact subset of those artifacts should be handed to an AI agent for one unit of work.

Without this, prompts may include:

- too much context
- irrelevant context
- conflicting context
- missing mandatory context

### Candidate framework additions

- a context-packaging rule or guidance document
- a standard structure for required, optional, and excluded context
- task-type-specific packaging guidance
- delivery-mode-specific packaging guidance
- packaging examples for implementation, review, and planning tasks

### Suggested definition areas

- required context for each task class
- optional supporting context
- forbidden or non-essential context
- maximum recommended context breadth
- source-of-truth rules for each included artifact

### Success criteria

- each task type has a defined context bundle model
- the framework can explain why each artifact is included or excluded
- implementation prompts become narrower and more task-specific
- duplicated or low-value context is reduced

### Priority

Highest

## Backlog item 2: Explicit artifact precedence and conflict-resolution rules

### Objective

Define a deterministic hierarchy for how the framework resolves conflicting guidance across artifacts.

### Problem being solved

The current framework implies precedence, but it does not yet state it sharply enough for consistent AI consumption.

When artifacts conflict, AI agents may behave inconsistently unless the framework clearly defines which source wins.

### Candidate framework additions

- an artifact precedence model
- conflict-resolution guidance for prompt generation
- a rule set for initiative-specific versus generic guidance
- examples of common conflict scenarios

### Suggested definition areas

- planning versus architecture precedence
- readiness versus task-detail precedence
- quality-gate constraints versus implementation convenience
- initiative artifact versus template precedence
- human approval status as a precedence factor

### Success criteria

- the framework has a published precedence order
- common artifact conflicts have a documented resolution path
- generated prompts and handoffs use consistent authority rules
- review feedback about contradictory guidance decreases

### Priority

Highest

## Backlog item 3: Context drift detection for downstream handoff

### Objective

Make the framework explicitly detect when task or handoff context has become stale because upstream source artifacts changed.

### Problem being solved

A handoff package may be structurally complete but still invalid if source context changed after it was generated or approved.

This creates hidden risk, especially when:

- requirements evolve
- architecture decisions change
- quality-gate outcomes are revised

### Candidate framework additions

- a drift-detection rule set
- a definition of which upstream changes invalidate which downstream artifacts
- a stale-context marker or review-needed state
- refresh guidance for impacted artifacts

### Suggested definition areas

- what counts as a material upstream change
- which artifacts must be rechecked after each change type
- whether drift blocks implementation or triggers warning-only review
- how to record the freshness state of handoff artifacts

### Success criteria

- the framework can identify when handoff context is stale
- downstream artifacts have a visible freshness status
- users know when regeneration or re-review is required
- implementation from outdated task context is reduced

### Priority

Highest

## Backlog item 4: Retrieval guidance by task type, role, and delivery mode

### Objective

Define what context should be loaded for each major activity instead of relying only on artifact availability.

### Problem being solved

The framework defines what should exist, but it is less explicit about what should be retrieved for a given downstream action.

This matters because context selection should vary by:

- implementation versus review
- OpenSpec versus standalone delivery
- greenfield versus brownfield
- product-owner versus coding-agent versus architect usage

### Candidate framework additions

- retrieval guidance by activity type
- role-specific loading rules
- brownfield-specific retrieval rules
- small-change fast-path retrieval rules
- a minimal-context and expanded-context model

### Suggested definition areas

- section-level retrieval guidance, not just whole-document inclusion
- mandatory retrieval for governed boundaries
- retrieval rules for optional visuals
- retrieval priorities under context-window constraints

### Success criteria

- each major workflow action has context retrieval guidance
- role-based context loading becomes more consistent
- critical sections are less likely to be omitted
- low-value document loading decreases

### Priority

High

## Dependencies across Wave 1 items

The Wave 1 items build on each other and should not be treated as independent.

Recommended dependency order:

1. per-task context packaging model
2. artifact precedence and conflict-resolution rules
3. context drift detection
4. retrieval guidance by task type, role, and delivery mode

Reasoning:

- packaging defines the target structure
- precedence defines authority inside the package
- drift detection protects the package over time
- retrieval guidance operationalizes the package across actual workflow situations

## Suggested delivery sequence

### Phase 1

- define packaging model
- define precedence model

### Phase 2

- define drift-detection rules
- define retrieval guidance

This split keeps the first phase conceptually tight around context authority and structure, while the second phase focuses on operational behavior.

## Suggested acceptance view for Wave 1

Wave 1 should be considered successful when the framework can answer these questions clearly:

- For this task, what exact context should the AI receive?
- Which artifact has authority if two sources disagree?
- Is the current task context still fresh?
- What should be loaded for this role and this workflow step?

If those four questions can be answered consistently, the framework will have made a meaningful step from artifact-driven governance toward context-driven AI delivery.
