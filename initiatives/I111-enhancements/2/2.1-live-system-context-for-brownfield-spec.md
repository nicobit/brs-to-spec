# Live System Context For Brownfield Spec

This document defines a first draft of the framework's model for incorporating live system context into brownfield and existing-system enhancement work.

Its purpose is to make the framework more grounded in implementation reality when the initiative affects an existing system.

## Objective

Define how the framework should incorporate live system context alongside narrative, planning, and architecture artifacts for brownfield delivery.

The goal is to ensure that downstream AI-assisted work receives context that reflects:

- actual implementation structure
- actual boundary and compatibility constraints
- actual operational and regression sensitivities

## Problem statement

Brownfield delivery carries risks that are often not fully visible in business intake, architecture summaries, or delivery planning alone.

Important constraints frequently live in the current system itself, such as:

- repository structure
- integration conventions
- test patterns
- configuration behavior
- deployment topology
- rollback sensitivity

Without explicit handling of live system context, the framework may remain too document-first for brownfield work.

## Scope

This spec applies to:

- existing-system enhancement initiatives
- brownfield architecture review
- readiness-sensitive brownfield delivery
- downstream task packaging for changes to existing systems

This spec does not yet define:

- tooling integrations
- repository-scanning implementation
- runtime telemetry ingestion
- automation behavior

It defines the framework concept and rules only.

## Core principle

For brownfield work, the current system is part of the source material.

Context should therefore come from both:

- declared intent in framework artifacts
- observed reality in the current implementation environment

## Live system context categories

The framework should treat the following as candidate live system context categories.

### 1. Structural context

Examples:

- repository layout
- module boundaries
- component ownership boundaries
- dependency organization

### 2. Interface and contract context

Examples:

- API definitions
- event schemas
- data ownership boundaries
- integration patterns

### 3. Implementation convention context

Examples:

- coding patterns
- test placement and style
- naming conventions
- configuration conventions

### 4. Operational context

Examples:

- deployment topology
- runtime dependencies
- monitoring dependencies
- rollback sensitivity
- operational coupling

### 5. Stability and compatibility context

Examples:

- fragile areas
- backward-compatibility constraints
- migration sensitivity
- regression-sensitive touchpoints

## Brownfield retrieval rule

When the initiative is an existing-system enhancement, the framework should elevate live system context during:

- architecture review
- readiness assessment
- handoff generation
- implementation task packaging

It should not treat live system context as optional if compatibility or regression risk is material.

## Brownfield packaging rule

Where live system context is relevant, task packages should include focused excerpts or summaries of the most decision-relevant implementation reality.

Examples:

- affected module or repository area
- impacted contract or schema excerpt
- applicable test or validation pattern
- deployment or rollback sensitivity note

The package should remain selective. The goal is not to dump repository state into the prompt.

## Interaction with existing artifacts

Live system context should complement, not replace:

- `architecture/architecture-review.md`
- `architecture/architecture-rules.md`
- `architecture/existing-system-impact.md`
- `engineering-readiness/readiness-check.md`
- active handoff artifacts

It should help validate whether those artifacts match actual system reality.

## Suggested brownfield context questions

For brownfield initiatives, the framework should be able to surface questions such as:

- what existing modules or components are actually affected?
- what current contracts must remain stable?
- what implementation conventions must the change follow?
- what tests or validation patterns already govern this area?
- what operational dependencies or rollout sensitivities exist?

## Minimum usage model

At minimum, the framework should support:

- identifying when live system context is needed
- identifying what kind of live system context matters
- carrying the relevant findings into downstream packaging

## Relationship to freshness

Live system context should also be treated as drift-sensitive.

If the framework later formalizes system-derived context, it should account for the fact that observed implementation reality may change over time and may need revalidation.

## Relationship to precedence

Live system context is not automatically authoritative by itself.

Its role depends on how it is used:

- as supporting evidence when interpreting planned work
- as a trigger for correcting stale or incomplete assumptions
- as an input to updated architecture, readiness, or handoff decisions

Once reflected in approved initiative artifacts, those artifacts remain the governing source.

## Success criteria

This model will be useful when:

- brownfield work includes real implementation context, not only declared architecture
- regression and compatibility risks are surfaced earlier
- downstream AI tasks are better aligned with current system reality
- brownfield handoffs require less rediscovery by engineers

## Open questions for next iteration

- what live system context categories should be mandatory first?
- how should system-derived findings be summarized into stable artifacts?
- how should multi-repository brownfield context be partitioned?
- which brownfield changes require operational context by default?

## Recommended next step

The next design step after this spec should be to define a context suitability scoring model so the framework can evaluate not just whether context exists, but whether it is shaped well enough for AI use.
