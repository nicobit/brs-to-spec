# Context Loss Controls Across Stage Transitions Spec

This document defines a first draft of the framework's model for preserving high-value context across workflow stages.

Its purpose is to reduce the loss of assumptions, rationale, tensions, and other nuanced information as work moves through the framework.

## Objective

Define how the framework should preserve meaningful context as initiatives move through:

- business intake
- planning
- architecture refinement
- readiness
- handoff
- implementation
- review

## Problem statement

Staged workflows improve structure, but they also create a risk that context gets flattened at each transition.

Common losses include:

- assumptions that remain active
- rationale behind non-obvious decisions
- known unknowns
- unresolved tensions
- rejected alternatives that still matter

When these are lost, downstream AI or human work may remain technically compliant while missing important intent.

## Scope

This spec applies to context preservation across stage transitions in the framework.

This spec does not yet define:

- metadata structures
- automation logic
- exact artifact schema changes

It defines the operating model and preservation rules only.

## Core principle

Traceability alone is not enough.

A context-driven framework should preserve not only what was decided, but also selected aspects of why it was decided and what uncertainty still remains.

## Context-loss categories

The framework should treat the following as high-value context that is at risk of being lost.

### 1. Active assumptions

Assumptions that continue to affect downstream work unless invalidated.

### 2. Decision rationale

Why a constraint, boundary, or design choice exists.

### 3. Known unknowns

Questions or uncertainties that remain unresolved but should stay visible.

### 4. Rejected alternatives

Alternatives that were considered and rejected, where that history still prevents repeated confusion or bad reintroduction.

### 5. Active tensions

Tradeoffs or conflicts that are not fully resolved but have downstream consequences.

## Preservation rule

Not all nuance must be copied forward.

Only context that continues to matter for downstream decision quality should be preserved.

The framework should therefore preserve:

- active assumptions
- decision rationale for non-obvious constraints
- unresolved issues that still affect execution or review
- rejected alternatives that guard against repeating known bad paths

It should avoid carrying forward:

- obsolete discussion history
- purely historical debate with no current downstream value
- redundant narrative that does not influence decisions

## Stage-transition guidance

### Intake to planning

Preserve:

- business assumptions that shape slicing
- exclusions and scope boundaries
- unresolved scope questions

### Planning to architecture refinement

Preserve:

- slice rationale
- dependency logic
- assumptions that affect component or boundary interpretation

### Architecture refinement to readiness

Preserve:

- non-obvious architecture constraints
- rationale behind key rules
- unresolved impacts that readiness must consider

### Readiness to handoff

Preserve:

- active constraints
- gate-driven conditions
- known risks and required validation concerns

### Handoff to implementation

Preserve:

- task-level assumptions
- design rationale where implementation judgment is required
- unresolved boundary sensitivities

### Implementation to review

Preserve:

- implementation assumptions made during execution
- deviations or tradeoffs introduced during coding
- residual risks

## Preservation methods concept

The framework should later support preservation through methods such as:

- carried-forward summaries
- explicit assumptions sections
- rationale notes attached to constraints
- unresolved-issues sections
- targeted cross-references rather than duplication

This spec does not prescribe the format yet.

## Relationship to packaging

Packaging should be able to include preserved nuance where it materially improves execution quality.

Examples:

- rationale for an architecture rule
- known unknowns affecting a review decision
- active assumption that shapes test expectations

## Relationship to retrieval

Retrieval should not load all preserved nuance by default.

Instead, retrieval should include preserved context selectively when:

- the task is architecture-sensitive
- the task involves tradeoffs or unresolved areas
- brownfield or operational risk is elevated

## Relationship to suitability

Preserved nuance can improve suitability when it reduces ambiguity.

However, excessive preserved detail can reduce suitability if it overwhelms the task package.

The framework should therefore preserve selectively and retrieve selectively.

## Success criteria

This model will be useful when:

- important assumptions and rationale remain visible downstream
- users and AI agents rediscover fewer already-known decisions
- implementation and review work reflect not just outputs, but key decision context
- the framework loses less nuance as work advances stage by stage

## Open questions for next iteration

- which nuance categories should be mandatory to preserve first?
- where should preserved rationale live without causing duplication?
- how should unresolved tensions be represented without blocking progress unnecessarily?
- how should preserved nuance be refreshed when upstream decisions change?
